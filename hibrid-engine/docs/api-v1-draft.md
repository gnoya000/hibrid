# V1 data model and API draft

**Status: draft for review. Nothing here is implemented.**

This is the contract the mobile client will be built against. It covers the
account model, what is stored server-side versus what stays on the device, the
new domain types V1 needs, and the endpoints for the four V1 user stories.

Security is deliberately out of scope for this draft — see §7. The goal here is
that the **data model and the API shape are future-proof**, so that adding
credential recovery, real accounts, and a social layer later is additive rather
than a migration.

---

## 1. The account key

The device holds one secret: an **account key**, generated by the server at
first launch. The server holds everything else, keyed by that secret.

```
Device                              Server
──────                              ──────
account_key ───────────────────────► resolves to account_id
                                     └─ profile, preferences, goals
health bucket ─────────────────────►    plans, routines
(sent per request, never stored)        training log, progress
```

This replaces the earlier "send everything on every request" sketch. The reasons
it is better are practical rather than philosophical: the training log no longer
travels on every call, progress no longer needs a device-held summary object to
stay bounded, and a lost phone stops being a lost training history the moment
key backup exists.

### The one property that makes the existing schema work unchanged

**The client never sends a `user_id`. The server resolves it from the key.**

That single rule means every model in `hibrid.user` is already correct as-is.
`TrainingSession.user_id`, `ExercisePerformanceRecord.user_id` and the
ownership validators on `User` all keep their current meaning and stay
load-bearing — the server fills them in from the resolved account, and the
validator catches a genuine cross-account bug rather than being a formality.

`Account.account_id` **is** `UserProfile.user_id`. There is no second identity
to reconcile.

Wire models still omit `user_id` from request bodies (a client has no business
asserting one), but they do it by injecting the *resolved* id, not a sentinel.
A client that sends one gets a 400.

## 2. The account model

New module, `src/hibrid/user/account.py`. Identity is user-schema material, not
persistence-layer material, so it belongs alongside `UserProfile`.

```python
class CredentialKind(str, Enum):
    DEVICE_KEY = "device_key"   # V1: the only kind
    EMAIL = "email"             # modelled, not implemented
    OAUTH = "oauth"             # modelled, not implemented


class AccountCredential(HibridModel):
    credential_id: UUID
    kind: CredentialKind
    lookup_hash: str            # see note below
    created_at: datetime
    last_used_at: datetime | None = None
    revoked_at: datetime | None = None


class Account(HibridModel):
    account_id: UUID            # == UserProfile.user_id
    created_at: datetime
    credentials: tuple[AccountCredential, ...] = ()
    display_handle: str | None = None   # reserved for the social layer
```

Three future-proofing decisions, all of which cost nothing now:

- **Credentials are a collection, not a column.** Adding email recovery later
  means inserting a second `AccountCredential` row, not altering `Account`.
  This is the whole reason the upgrade path HANDOFF describes ("anonymous
  device accounts, upgradeable to a real account before social lands") stays
  open.
- **`lookup_hash` is named for what it will hold, not what V1 puts in it.** V1
  stores the key verbatim and looks it up directly. Moving to `SHA-256(key)` is
  then a data migration with no schema change. Naming it `secret` today would
  guarantee a rename later.
- **`display_handle` is reserved and unused.** The social layer needs a subject
  that is not the account key; leaving the slot empty is free, retrofitting a
  public identifier onto live accounts is not.

## 3. What is stored, and what is not

This split is the safeguard, and it is the same one the project already
enforces at the API boundary today. Reasoning is in
[decisions.md](decisions.md#health-data-stays-on-the-device).

### Stored server-side, keyed by `account_id`

| Data | Models |
|---|---|
| Identity | `Account`, `AccountCredential` |
| Who they are | `UserProfile`, `TrainingBackground` |
| What they want | `TrainingGoal`, `ObjectiveWeights`, `PerformanceTarget`, `TargetEvent` |
| What their life allows | `TrainingPreferences`, `AvailabilityWindow`, `EquipmentAccess` |
| What to do | `TrainingPlan`, `PlannedSession`, `Routine`, `RoutineEntry` |
| What they did | `TrainingSession`, `PerformedExercise`, `PerformedSet` |
| Derived caches | `ExercisePerformanceRecord`, `TrainingLoadSummary`, `ProgressState` |

### Never stored server-side — device-held, sent per request, forgotten

| Data | Models |
|---|---|
| Health constraints | `HealthProfile`, `Injury`, `MedicalConsideration` |
| Biometrics | `BodyComposition`, `RecoveryReading`, `WellnessCheckIn`, `CardiovascularFitness`, `FitnessAssessment` |

Two consequences worth stating explicitly, because both are easy to get wrong:

**`User` stops being a stored object.** It remains the complete *logical* view
and stays exactly as it is — but it is now composed in memory, per request, from
the stored half plus whatever the device sent. Nothing loads or saves a `User`.
Its ownership validator is still the right check at composition time.

**The objective bars are not a `FitnessAssessment`.** These are two different
things and the distinction matters: `FitnessAssessment` records a *measured*
testing battery — a real assessment the user performed — and belongs to the
device-held biometric bucket. The bars are *derived from the stored training
log*. They live in `ProgressState`, keyed by the same `TrainingObjective` enum so
the two remain comparable dimension by dimension, which was the point of keying
`component_scores` that way in the first place.

This matters most for the level bar (§4): when its formula is specified, a
measured `FitnessAssessment` would be the obvious input — and it is exactly the
input that is not available server-side. The level bar has to be derivable from
the training log alone.

## 4. New domain types

### `hibrid.models` — the weekly plan

`Routine` is a single session. A weekly plan needs a container, and it belongs
in `hibrid.models` alongside it, equally pure:

```python
@dataclass(frozen=True)
class PlannedSession:
    weekday: Weekday
    label: str                  # "Push", "Lower body", "Conditioning"
    routine: Routine

@dataclass(frozen=True)
class TrainingPlan:
    plan_id: UUID               # stable, like Routine.routine_id
    name: str
    sessions: tuple[PlannedSession, ...]
```

⚠️ **`Weekday` must move from `hibrid.user.enums` into `hibrid.models`**, and be
re-exported from its current home. `hibrid.user.enums` imports *from*
`hibrid.models`, so using `Weekday` here is a circular import. This is exactly
the treatment `Equipment` and `MovementPattern` already get, and defining a
second copy is ruled out by the never-fork-an-enum rule.

`Routine.routine_id` and `TrainingPlan.plan_id` finally have somewhere to
resolve against, which also closes `TrainingSession.prescribed_routine_id` —
a field that has pointed at nothing since it was written.

### `hibrid.progress` — a new pure module

Sits alongside `training_memory.py`, reads the same session log, holds no state.

**There is no streak.** The mechanic is a monotonic counter plus a decay rule, and
the reasoning is worth stating because it inverts the usual design: a streak
punishes absence by an arbitrary rule the app invented, whereas **detraining is
real physiology**. A level bar that falls after two weeks off is the app telling
the truth, not enforcing a rule — so it can afford to have consequences where a
streak could not.

```python
@dataclass(frozen=True)
class ActivityCounter:
    """Lifetime totals. Monotonic — these never decrease."""
    total_sessions_logged: int
    total_working_sets: int
    total_volume_load_kg: float
    sessions_last_7d: int
    sessions_last_28d: int
    first_logged_at: datetime | None
    last_logged_at: datetime | None
    days_since_last_session: int | None
```

Every logged session moves these up and nothing moves them down. Milestones
(10th, 50th, 100th session) are `achievements_unlocked` — positive reinforcement
on every log, with no failure state to hit.

**Two bars per objective**, because "how often do I train hypertrophy" and "how
much hypertrophy do I have" are different questions and one number cannot answer
both:

```python
@dataclass(frozen=True)
class EngagementBar:
    """How often the user trains this quality. Rolling 28-day window."""
    objective: TrainingObjective
    score: float                  # 0-100
    delta_28d: float
    sessions_28d: int
    evidence: str

@dataclass(frozen=True)
class LevelBar:
    """How much of this quality the user has. Cumulative, decays with inactivity.

    NOT YET SPECIFIED — the field shape is fixed so the API and the client can be
    built against it; the formula is open. `score` is None until it lands, which
    is honest rather than a placeholder zero."""
    objective: TrainingObjective
    score: float | None           # 0-100; None = not yet computable
    delta_28d: float | None
    decay_multiplier: float       # 1.0 = no decay applied
    inactive_days: int
    evidence: str

@dataclass(frozen=True)
class ObjectiveProgress:
    objective: TrainingObjective
    engagement: EngagementBar
    level: LevelBar
```

`evidence` is not decoration. A bar the user cannot interrogate is one they will
not trust — the same reasoning that makes `BaselineComparison` carry its raw
inputs and `DoseOutcome` always say why an entry did not move.

### Attributing work to an objective

Both bars need to know which logged sets count as hypertrophy work, and
`TrainingSession` does not record what it served. **V1 infers the objective from
the performed rep count.**

**Attribution reads the dose, never the exercise's provenance.** Which source
library or discipline an exercise came from says nothing about the quality it
trained on a given day — a 3-rep kettlebell clean is strength work, a 15-rep
barbell squat is not. Attributing by library would misclassify both and would
need a new mapping every time a discipline is added.

The implementation is a reuse: `ObjectiveStrategy` already owns a `rep_range` per
objective, so attribution is "which strategy's rep range contains this set".
Tuning a strategy's range moves attribution with it, and there is one source of
truth rather than two that can drift.

The function should return `ObjectiveWeights` rather than a single objective,
even while V1 fills it with a hard 1.0 bucket. The type already exists, already
normalises, and a 12-rep set genuinely sits on the hypertrophy/endurance
boundary — so a later softening changes the values, not the signature or any
caller. Same future-proofing as `LevelBar.score` being nullable.

Two accepted limits: rep count cannot tell a heavy triple from a
technically-limited one (load relative to the 1RM M8a already estimates would be
better), and it only works for `RepsDose` — a 60-second plank and a 60-second
hamstring stretch are the same dose shape and different qualities. Separating
those needs `Exercise.modality` as a second input, which is a property of the
*movement* rather than a label of its origin, so it does not violate the rule
above. Nothing needs it until the dose search lands in V2.

### The decay rule

Named, inspectable constants, following the pattern of the readiness multipliers:

```python
DECAY_GRACE_DAYS = 14        # nothing decays before this
DECAY_RATE_PER_WEEK = ...    # open, per objective
DECAY_FLOOR = ...            # a level never falls to zero
```

Four properties this rule must have:

- **It applies to `LevelBar` only.** `EngagementBar` is a rolling 28-day window,
  so it already decays by construction — adding an explicit rule on top would
  decay it twice. `ActivityCounter` never decays at all.
- **It is computed on read, never written by a scheduled job.** Decay is a pure
  function of `days_since_last_session` and `as_of`. A cron job mutating scores
  overnight would break reproducibility, and it produces the worst possible bug
  class: a number that changed while the user was asleep and cannot be explained
  afterwards.
- **The rate is per objective.** Different qualities detrain at genuinely
  different rates — cardiovascular fitness falls fastest, maximal strength is
  retained longest. One shared constant would be wrong for most of the enum.
- **`decay_multiplier` and `inactive_days` travel in the response.** The client
  must be able to say *"down 8% after 3 weeks off"* rather than showing a
  silently smaller bar.

Because decay is recomputed from the log on every read, changing the curve later
recomputes all history. There is no migration and no wrong data left behind — an
argument for shipping a defensible rule now rather than deferring it.

`ProgressState` is the stored, recomputable cache of all of this — the same
relationship `ExercisePerformanceRecord` has to `TrainingMemory`.

## 5. Endpoints

`Authorization: Bearer <account_key>` on everything except `/health`,
`/objectives` and `/exercises/*`, which carry no user data.

### Account

| | |
|---|---|
| `POST /accounts` | No body. Creates an account, returns `{account_key, account_id}`. Called once, on first launch. |
| `GET /me` | Profile, background, preferences, goals. |
| `PUT /me/profile` · `PUT /me/preferences` · `PUT /me/goals` | Replace each. |

### Story 1 — generate my weekly routine

```jsonc
POST /plans/generate
{
  "objective": "hypertrophy",          // single, until M4 lands
  "environment": "commercial_gym",     // which EquipmentAccess applies
  "seed": 918273,                      // required; the device owns it
  "health": { /* HealthProfile | null — device-held, request-scoped */ }
}
```

Profile, background and preferences come from the account — the client does not
resend what the server already holds. Health does not live there and therefore
travels in the body.

The response is the stored `TrainingPlan` plus a **`generation_report`**:

```jsonc
{
  "plan": { "plan_id": "…", "name": "3-day full body", "sessions": [ … ] },
  "generation_report": {
    "sessions_requested": 4,
    "sessions_produced": 3,
    "unmet_constraints": [
      { "constraint": "sessions_per_week_target",
        "detail": "availability supplies 3 weekdays; 4 were requested" }
    ],
    "context_filter": { "permitted": 2841, "total": 4531, "permitted_fraction": 0.627 },
    "starting_load_policy": "conservative"
  }
}
```

`generation_report` is the part to insist on. A plan that silently drops a
requested session reads as a bug; the same instinct that makes every unvaried
entry report a `DoseOutcome` applies here. And `starting_load_policy` lets the
client say "we start you light on purpose" rather than letting a deliberately
conservative first prescription read as the app underestimating the user.

**Engine work: M5, plus `TrainingPlan` and the `Weekday` move.**

#### Built ahead of it: one session, on demand

`POST /sessions/generate` and `POST /sessions/blocks/vary` exist today, and they
are the single-session slice of the same milestone. They are worth knowing about
before implementing `/plans/generate`, because the weekly endpoint should compose
them rather than reimplement generation.

```jsonc
POST /sessions/generate
{
  "muscles": ["pectorals", "lats"],    // what to train, in order
  "duration_minutes": 60,              // the budget the session must fit
  "difficulty": "challenging",         // light | moderate | challenging,
                                       //   relative to the user's own baseline
  "objective": "hypertrophy",          // single, until M4 lands
  "seed": 918273,
  "body_mass_kg": 80.0,                // device-held; only for a starting load
  "background": { /* TrainingBackground — skill ceiling + familiar movements */ },
  "context": { /* health, preferences, environment, recovery */ },
  "history": { /* session log — remembered loads and the acute:chronic ratio */ }
}
```

The response is a session of **blocks** plus a `report` in the same spirit as
`generation_report` above: `muscles_uncovered`, `fits_time_budget`,
`starting_load_policy`, `is_prescribable`, and a typed `unmet_constraints` list.

Three properties of the contract are worth carrying into the weekly endpoint:

- **A block is the unit of re-rolling.** Each carries an `index`, its own
  `volume` and `time_seconds`, and a `time_budget_seconds`. Post one back to
  `POST /sessions/blocks/vary` and both invariants come back preserved, so the
  session's three requested parameters survive any number of re-rolls. This is
  the same guarantee as `alternatives_per_entry` in Story 3 approached from the
  other side: one committed change rather than a list to choose from.
- **`difficulty` is `SessionIntent`, and it is stated once.** Sending it both
  top-level and inside `context.session_intent` with different values is a 422
  rather than a silent preference. Re-rolling deliberately takes no difficulty at
  all — the block's numbers already embody it.
- **Every load says where it came from.** `load_source` distinguishes a
  remembered load, a deliberately light body-mass fraction, a correct 0 kg on a
  bodyweight movement, and no basis at all. The last of those sets
  `is_prescribable: false`; it must never be shown as a 0 kg prescription.

`POST /sessions` in Story 3 is workout *logging* and unrelated despite the shared
prefix. Neither generation endpoint stores anything.

**Engine work: none remaining — `session_generation.py`.**

### Story 2 — visualise every individual session

| | |
|---|---|
| `GET /plans` | The account's plans, summarised. |
| `GET /plans/{plan_id}` | Full plan, every session resolved: exercise names, `describe()` strings, per-entry volume and time, session and weekly totals. |
| `GET /plans/{plan_id}/sessions/{weekday}` | One session, same resolution. |
| `GET /exercises/{exercise_id}` | Exercise detail for the movement screen. |
| `POST /exercises/lookup` | `{"exercise_ids": [...]}` → many in one round trip. POST, not a query string, because a full week of ids is long and query strings land in access logs by default. |

There is **no exercise endpoint at all today**, which blocks the exercise-detail
screen outright. It returns `id`, `name`, `target`, `secondary_muscles`,
`equipment`, `movement_pattern`, `modality`, `unilateral`, plus the enrichment
attributes — nulls included and honest, per the coverage caveat in
[known-gaps.md](known-gaps.md).

`GET /plans/{plan_id}` optionally accepts a `health` query context so a stored
plan can be re-checked against constraints that changed since it was generated
(a new injury) and flagged per entry. That reuses `VariationContext.permits`
with no new engine work.

**Engine work: none. Retrieval and reshaping only.**

### Story 3 — variation and suggestions

| | |
|---|---|
| `POST /plans/{plan_id}/vary` | Varies the whole plan. Load multiplier computed **once for the week** and applied across it — computing readiness per session would apply one morning's HRV reading to Saturday. |
| `POST /plans/{plan_id}/sessions/{weekday}/vary` | One session. Today's `/vary`, reading the stored routine and log. |
| `POST /sessions` | **Log a completed workout.** `TrainingSession` + `PerformedExercise` + `PerformedSet`. Everything downstream derives from this row, so it is the one most worth getting right — in particular, RPE from the very first session, or progression has nothing to read. |
| `GET /sessions` | The log, paged. |

Both vary endpoints take the device-held health block in the body and read
everything else — routine, log, preferences — from storage. They gain one knob:

```jsonc
"alternatives_per_entry": 3   // default 0, which preserves today's behaviour exactly
```

Each varied entry then carries `alternatives: [{exercise_id, exercise_name,
similarity, dose, rationale}]`, which is what turns a variation into a
*suggestion the user can choose from*. `find_substitutes` already ranks and
returns a scored band, so this surfaces what the engine currently discards —
but it is still a real change to `variation.py`'s return type.

**Engine work: `alternatives_per_entry` only. The rest is API-layer.**

### Story 4 — gratification

| | |
|---|---|
| `GET /progress` | Lifetime counter, two bars per objective, adherence, personal records, achievements. |

```jsonc
{
  "counter": {
    "total_sessions_logged": 87, "total_working_sets": 1964,
    "total_volume_load_kg": 412300.0,
    "sessions_last_7d": 3, "sessions_last_28d": 11,
    "last_logged_at": "2026-08-11T18:22:00Z", "days_since_last_session": 1
  },
  "objectives": [
    { "objective": "hypertrophy",
      "engagement": { "score": 72.0, "delta_28d": 4.5, "sessions_28d": 9,
                      "evidence": "18 working sets/week in hypertrophy rep ranges, up from 14" },
      "level":      { "score": null, "delta_28d": null,
                      "decay_multiplier": 1.0, "inactive_days": 1,
                      "evidence": "level scoring not yet specified" } }
  ],
  "consistency": { "sessions_completed": 11, "sessions_prescribed": 12,
                   "adherence_rate": 0.917 },
  "personal_records": [
    { "exercise_id": "0025", "exercise_name": "Barbell Bench Press",
      "estimated_one_rep_max_kg": 92.5, "achieved_on": "2026-08-05T18:22:00Z",
      "is_new": true }
  ],
  "achievements_unlocked": ["fifty_sessions"]
}
```

Pure function of the stored log — no request body, and the earlier draft's
device-held `carry` object disappears entirely, along with the fact that it was
trivially forgeable. Server-authoritative progress is also the precondition for
leaderboards ever working, so this is the version that survives contact with V3.

**The client decides how to render two bars per objective.** The API's job is to
supply both honestly and say which is which; whether they appear stacked, paired
or on separate screens is a frontend decision.

**What is still open:** the `LevelBar` formula, and the per-objective decay rates
it feeds. The field shape is fixed, so the API and the mobile client can be built
against it now — `score: null` is the honest answer until the formula lands, and
never a placeholder zero that would render as a real reading of the user.

**Engine work: all of it — the new `hibrid.progress` module.**

## 6. What stays from the stateless design

Two properties are worth keeping even though they are no longer privacy
mechanisms:

- **`seed` is the device's job, never the server's.** The server must not
  default it to a clock read or `random()`. A device that wants a different
  plan sends a different seed; one that wants yesterday's plan back sends
  yesterday's seed. It also gives the mobile team free regression tests.
- **`as_of` stays an explicit parameter.** Already true across the engine and it
  must remain so — an endpoint reading `datetime.now()` cannot reproduce a past
  prescription, which is what makes "why did it tell me that last Tuesday?"
  answerable.

## 7. Out of scope for this draft

Deliberately deferred, and accepted:

- **No key security.** No keychain or keystore integration, no hashing at rest,
  no rotation, no rate limiting. The model has the shape for all of it (§2);
  none of it is built.
- **Lost device or lost key means the account is lost.** Accepted for now.
  There is no recovery path, because any real one needs a second factor, which
  needs an identity. The credential model is what keeps that door open.
- **No encryption at rest, no DSAR or erasure tooling.** Needed before public
  launch, not before the client can be built.

The point of the draft is that none of the above requires the data model or the
endpoint shapes to change when it does arrive.

## 8. Summary

| Story | Endpoints | Engine work |
|---|---|---|
| 1. Generate weekly routine | `POST /plans/generate` | `TrainingPlan`, move `Weekday`. **M5's single-session half is built** — `POST /sessions/generate`, `POST /sessions/blocks/vary` |
| 2. Visualise each session | `GET /plans`, `GET /plans/{id}`, `GET /plans/{id}/sessions/{weekday}`, `GET /exercises/{id}`, `POST /exercises/lookup` | None |
| 3. Variation and logging | `POST /plans/{id}/vary`, `POST /plans/{id}/sessions/{weekday}/vary`, `POST /sessions`, `GET /sessions` | `alternatives_per_entry` |
| 4. Gratification | `GET /progress` | **All** — new `hibrid.progress` |
| Account | `POST /accounts`, `GET /me`, `PUT /me/*` | None |
| Reference | `GET /objectives`, `GET /health` | Unchanged |

`GET /routines` and `GET /routines/{name}` read sample YAML from the repo. They
have no product role once plans are stored — keep them behind a dev flag as
playground fixtures, or drop them, but do not let the client build against them.

Two of the four stories are API-layer work over an engine that already does the
hard part. Progress is now the one genuine remaining engine gap: generation's
single-session half landed as `session_generation.py`, leaving the weekly plan
container rather than the generation logic. The build order in
[HANDOFF.md](../HANDOFF.md) reflects the same split.
